# Light, scenes, device lock

Area documentation of ComfyOS – part of the guide `CLAUDE.md` (which says when to read this file).
This file says how the area is built and what to watch out for when changing it; version notes ("since 0.x") name
when something was added.

## Since 0.20

- **`control.py` (split off from `core.py`):** device commands, lights, scenes, effects and the lock check now live there
  (`apply_device`, `send_light`, `apply_lights`, `apply_scene`, `apply_house`, `stop_scene`, `apply_effect`, `scene_step`,
  `scene_loop`, `check_lock` …). **`core.<name>` stays the facade** – routes and tests keep calling `core.apply_scene`
  and so on. `control.py` reads `core.publish`, `core.all_devices`, `core.scene_step` through the module at runtime because tests
  replace them (`test_style` section 4).
- **Switchability in one place:** `HO.canControl(d)` (reachable, with a control channel, not locked) – `switchable`,
  `groupSwitchable` and `HO.lights.controllable` build on it.

## Structure and rules

- **Light control (since 0.12; `light_model.py` = generic light model of the core, CLIP bodies have been built by the Hue plugin in `clip.py` since 0.18):**
  - Every dimmable lamp of a plugin carries `light = {caps: {ct, color, gradient, gradient_modes, effects, effect_params}, mode: ct|xy|gradient, xy, mirek, points, gmode, effect}` (from `plugin_api.LightState` through `device_merge.light_dict`; for Hue from `clip.read_light_state`, events through `clip.apply_light_update`). Plugs and Home Base lamps have `light = None`.
  - **One path for all light commands:** `core.send_light` (interface, scenes, flow) → `plugins.command`. The command format is `{on, brightness, kelvin|mirek, color "#rrggbb"|xy, gradient|gradient_xy, gradient_mode, effect, effect_color|effect_mirek|effect_speed, duration}`. The plugin translates it (Hue: `clip.build_command` builds the CLIP v2 body and falls back to what is possible: colour → white tone → brightness only).
  - Home Base lamps can only do on/off. There is no verified capture for dimmer and colour items of the Home Base, therefore no values are written there.
  - Colours are stored as `#rrggbb`, the bridge gets CIE xy. JS (`core.js`) and Python compute with the same formulas.
  - Never send light commands to the bridge faster than ~10/s (`asyncio.sleep(0.1)` between lamps, throttled in the UI).
- **Scenes (`scenes_store.py` → `data/scenes.json`, `api/scenes.py`, frontend `js/lights.js` = page "Szenen" (route `#light`) + `HO.lights.*`):**
  - **Room tiles (since 0.13.1):** always open – **not collapsible** (was a misunderstanding, do not build it in again). **Columns and arranging (since 0.19.3, replaces the sort handle):** `#devBox` is an `HO.tileGrid` (key `home`, tiles `.room-card` with `id` `rc-<room>`) – 1–3 columns per device (`ho.cols.home`, selection in the header "Geräte", one on the phone), "Anordnen"/"Automatisch" as on the system page, stored per column count in `settings.json` `layout.home` (comes with `/api/overview` as `layout_home`). "Anordnen" switches the filter to "Alle" (otherwise filtered-out rooms would be missing in the stored arrangement); while it runs, `partial()` does not redraw `#devBox`, otherwise `rgrid.refresh()` after every redraw. The former order from `rooms.json` (`room_order`) is only the default order without an own arrangement; the interface no longer writes `PUT /api/rooms/order` (route and test C10 still exist – candidate for removal). Arranging is pure display: it creates no rooms, renames nothing and leaves `names` untouched.
  - **Places of operation (since 0.12.3):** starting/controlling happens in the room cards of the home page (`overview.js` `roomCardHTML`: header of fixed height with the scene image or `HO.lightGlow`, room switch, brightness, scene chips, lamp rows `HO.lights.lampRowHTML`, other devices as `.tiles.sm`). Tapping the header → `HO.lights.roomSheet(roomId, ops)` (the home page passes its optimistic switches through as `ops`; `HO.lights.onData` redraws the open sheet). The page "Szenen" only manages: header without a tile with "Import" (menu: "Von der Hue Bridge") and "Neu", the studio card (since 0.19.2 only open while something is being edited: "Neu" or tapping a scene; save, delete, cancel close it) + library with the tabs Alle/ComfyOS/Hue.
  - **Origin:** `source: "hue"` on bridge import. `source`/`image_rid` never come from the editor; `scenes_store.update` keeps them (`KEEP_ON_UPDATE`).
  - **Scene images:** `image_rid` = `metadata.image.rid` (`public_image`) of the bridge. Fetched only through `GET /api/hue/image/{rid}` (`HueBridge.fetch_image`: only JPEG/PNG/WebP, cache, a failed attempt is blocked for 10 min; if the bridge delivers none → 404 + once the event "Hue Bridge liefert keine Szenenbilder"). In the browser `HO.lights.imgTag` with the gradient/room light as a replacement on error. No images from the internet without an egress entry and asking first.
  - **Bridge import:** the same scene in several rooms/zones of the bridge = one entry (`groups` = all rooms, only as a note in the dialog). **Imported scenes get no room assignment (since 0.17)** – the rooms of the bridge are not those of ComfyOS, assignment happens in the scene studio. **No sync back to the bridge** (deliberate, unlike the Magenta sync): ComfyOS switches the lamps itself, the bridge does not need the scenes; here a scene is a palette, on the bridge a fixed lamp list per room – a sync would distort room variants and palettes and write into the user's Hue app.
  - A scene is a palette `[{c|ct, b}]`, not a list of fixed lamp values. `light_model.scene_states` distributes the colours in order over the lamps (sorted by name). Gradient lamps get several colours.
  - **Room assignment (since 0.15, `scenes.json` `version: 2`):** `rooms` is a mandatory assignment – **empty = offered in no room**. **First assignment:** a fresh installation (state `version: 1`) does not know any rooms yet when the templates are created; `core.seed_scene_rooms` enters all rooms once for scenes without a room when `/api/overview` is loaded – except for imported Hue scenes (`scenes_store.seed_rooms`; without known rooms state 1 remains), afterwards `version: 2` applies. `_save` writes back the loaded `version` – never enter `VERSION` fixed, otherwise a fresh installation would skip the first assignment. That is no legacy: every new installation needs it. In the room `sceneRowHTML` only shows assigned scenes (plus the currently active one). `apply_scene` itself does not check the assignment (flows choose rooms explicitly).
  - **Room variants:** `variants[room] = {lamps: {device_id: {on, brightness, mirek|xy|gradient_xy|color}}, updated}` (`clean_lamp_state`, effects are not part of it). For room targets `apply_scene` lays the variant over the palette distribution (`_with_variant`); lamps without an entry get the palette, dynamic scenes keep rotating only the palette. "Für diesen Raum speichern" = `POST /api/scenes/{id}/variants/{room}` (also assigns the room), reset = `DELETE`, "Als neue Szene" = `POST /api/scenes/from-room/{room}` (`light_model.palette_from_lamps`: without duplicates, max. 9). `variants` is in `KEEP_ON_UPDATE` – the editor never sends them along.
  - **House scene:** `POST /api/scenes/{id}/apply-house` → `core.apply_house` = `apply_scene` for all assigned rooms with lamps (per room with variant). Chip row "Szene fürs ganze Haus" in the tile "Licht & Szenen" below the main tile (`houseScenesHTML` in `houseLightHTML`, since 0.19.2 together with all lights on/off), "Keine" = end all scenes.
  - **Effects (`effects_store.py` → `data/effects.json`, independent of scenes):** per room `{effect, target: "room"|[ids], color_source: own|scene|custom, color|kelvin, speed 0–100}`; `PUT|DELETE /api/effects/{room}` → `core.apply_effect`. Sent through `send_light` with `effect` + `effect_color|effect_mirek|effect_speed`; `light_model.command_body` builds CLIP v2 `effects_v2.action.parameters` from it, but only if the lamp has `effects_v2` (`caps.effect_params`) – otherwise silently only `effects` (own colours). `apply_scene` sends the effect again afterwards (a scene change keeps it running, scene colour anew). "Raum aus" (`apply_lights` off) forgets the effect. `scene_step` does not paint over lamps with a running effect. SSE `{"type": "effects", rooms}`, `/api/overview` delivers `effects`.
  - **Room header (since 0.15):** `data-room-head` (tappable, light setting) only for rooms with lamps; rooms without light have a plain heading (room details still through the floor plan).
  - **Targets:**
    - Rooms (`room:<id>`) and device groups of the floor plan (`group:<id>`) remember the active scene in `active`.
    - Single lamps are only set, without an active scene.
  - **Ending:** restores the `snapshot` from the start of the first scene. Room off or all lights off forgets the scene without restoring.
  - **Individually adjusted lamps:** every light command with colour or brightness through `apply_device` sets the lamp to `excluded`.
  - **Dynamic scenes:** `core.scene_loop` / `scene_step` only rotates colours, and only for lamps that are switched on and not excluded.
  - Templates are created once (`seeded`); deleted templates do not come back.
  - Scenes of the bridge are only imported as a palette (`GET /api/scenes/bridge`, `…/import`). ComfyOS recalls no bridge scenes.
  - Changes go out as SSE `{"type": "scenes", scenes, active}`. The home page gets the scenes through `/api/overview` (`scenes`).
  - Room background: `HO.lightGlow(devs)` produces a blurred gradient from the current light. Scene chips come from `HO.lights.sceneRowHTML({room|group|dev})`, they work everywhere through a global click handler. Tapping the active scene ends it.
  - Photo → palette only in the browser. The image is never uploaded.
  - Tests: `tests/core/test_scenes.py`.
- **Device lock (since 0.15, `device_store.py` → `data/devices.json` `{version: 1, locked: {id: {at, by: "user"|"flow:<id>"}}}`):** ComfyOS does not switch a locked device – user, flow, scene, house scene, effect, dynamic scene, "Alle Lichter". Enforced **on every switching path in the core**, because scenes and "Alle Lichter" bypass `apply_device`:
  - `core.check_lock(d, source)` in `apply_device` **and** `send_light` (last resort), plus `plugins.command` before every command to a plugin (since 0.18; `context.switch` from plugin routes runs through `apply_device`) → `device_store.DeviceLocked` (subclass of `HTTPException`, 423 "… ist gesperrt – im Gerätemenü entsperren.").
  - `core._lamp` leaves out devices with `locked` (scene targets, `apply_lights`, effects) – skipped, no error; `_run_states`/`apply_lights` catch `DeviceLocked` as "skipped"; `stop_scene` does not restore locked lamps; `scene_step` leaves them alone.
  - Only exception: `source == device_store.LOCK_SOURCE` (`"lock_node"`): the flow node "Gerät sperren" (`lock`, since 0.17). It locks/unlocks through `core.flow_set_lock` (source `flow:<id>`, event "… gesperrt durch Flow") and can switch in the process – even an already locked device (`apply_device(..., LOCK_SOURCE)`).
  - Flow: `flow_engine._hook` catches `DeviceLocked` → trace + event log "<Flow>: <Gerät> ist gesperrt", return `LOCKED`, **the flow keeps running** (no `last_error`).
  - API `POST /api/devices/{id}/lock|unlock` (the device must exist; event "gesperrt/entsperrt durch Nutzer", SSE `{"type":"device", id, locked}`); `merged_devices` attaches `locked`/`locked_by` (`device_store.apply`) and cleans up locks of vanished devices during the merge. `locked` is in `LIVE_FIELDS`.
  - Frontend: `HO.lockedBtn(d)` (greyed out, `data-locked`) – a capture handler in `lights.js` only shows `HO.LOCK_HINT`; padlock in the lamp row and the floor plan (`fp-badge lock`), on the tile **only once**: the greyed-out switch carries it, the mark `t-flag lock` only appears for devices without a switch (since 0.19, double before); switch "Gerät sperren" in the device sheet. `switchable`/`groupSwitchable`/`HO.lights.controllable` exclude locked devices.
  - The lock only affects ComfyOS (wall switch/Hue app/Magenta app keep switching) – the UI says so too. **New switching path ⇒ `check_lock` + section in `tests/core/test_device_lock.py`.** With the plugin system the command forwarding in the loader checks as well.
